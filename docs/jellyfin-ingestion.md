# Jellyfin ingestion architecture

This document expands issue #58 into an implementation contract. Jellyfin is a first-class WatchWeaver ingestion source and must be usable without Trakt.

## Goals

- Receive completed movie and episode watches from Jellyfin within normal event-delivery latency.
- Preserve distinct rewatches while making retries idempotent.
- Never require direct access to Jellyfin's database.
- Allow WatchWeaver to run with Jellyfin as its only watch-history source.
- Support separately built Jellyfin 10.11 and 12.0 plugin artifacts behind one protocol.
- Keep the WatchWeaver receiver stable enough that plugin upgrades do not require synchronized server releases.

## Component boundary

The Jellyfin plugin and WatchWeaver communicate only over a versioned HTTP API. The plugin owns Jellyfin event capture, local signal correlation, user filtering, and its durable outbound queue. WatchWeaver owns authentication, validation, media identity mapping, durable event deduplication, watch-history persistence, prompt evaluation, and connection status.

The plugin should live in a separate GPLv3-compatible repository/package because it links against Jellyfin components. WatchWeaver remains under its existing license. The HTTP event contract is the boundary between them.

## WatchWeaver HTTP contract

### Endpoint

`POST /api/v1/ingest/jellyfin/events`

Requests use JSON and a dedicated bearer token generated by WatchWeaver. The token is scoped only to Jellyfin ingestion and is not an administrator credential.

Recommended headers:

- `Authorization: Bearer <connection token>`
- `Content-Type: application/json`
- `Idempotency-Key: <event id>`
- `User-Agent: WatchWeaver-Jellyfin/<plugin version>`

The body also contains the event ID so queued events remain self-contained.

### Event envelope

```json
{
  "schema_version": 1,
  "event_id": "01J...",
  "event_type": "played",
  "occurred_at": "2026-09-03T16:00:00Z",
  "server": {
    "id": "stable-jellyfin-server-id",
    "version": "10.11.x"
  },
  "plugin": {
    "version": "0.1.0",
    "target_abi": "10.11.0.0"
  },
  "user": {
    "id": "jellyfin-user-id",
    "name": "optional display name"
  },
  "item": {
    "id": "jellyfin-item-id",
    "type": "episode",
    "title": "Episode title",
    "year": 2026,
    "series_title": "Series title",
    "series_id": "stable-jellyfin-series-id",
    "season_id": "stable-jellyfin-season-id",
    "season_number": 2,
    "episode_number": 4,
    "provider_ids": {
      "tmdb": "123",
      "imdb": "tt1234567",
      "tvdb": "456"
    }
  },
  "playback": {
    "played": true,
    "position_ticks": 36000000000,
    "runtime_ticks": 36000000000,
    "progress_percent": 100,
    "play_count": 2,
    "client": "Jellyfin Web",
    "device": "Browser"
  }
}
```

### Required fields

- `schema_version`
- globally unique `event_id`
- `event_type`
- `occurred_at`
- `server.id`
- `server.version`
- `plugin.version`
- `user.id`
- `item.id`
- `item.type`
- `item.title`
- `playback.played`

Episode events additionally require series title, season number, and episode number. Provider IDs are strongly preferred but cannot be mandatory because some libraries lack them.

### Event types

Initial protocol supports:

- `played`: a completed movie or episode watch.
- `marked_played`: a manual watched-state change when Jellyfin exposes enough information to distinguish it reliably.

Do not send playback-progress events to this endpoint. A normal stop below the completion threshold is not a watch event.

A future protocol may add `marked_unplayed`, but deletion semantics are intentionally excluded from the first receiver slice because an upstream state reversal is not equivalent to deleting an immutable historical watch event.

### Responses

- `202 Accepted`: new event durably accepted.
- `200 OK`: duplicate event already accepted; safe for the plugin to remove from its queue.
- `400 Bad Request`: malformed or unsupported payload. Include a stable machine-readable rejection code.
- `401 Unauthorized`: token absent/invalid/revoked.
- `409 Conflict`: event ID was previously accepted with materially different immutable identity fields.
- `413 Payload Too Large`: bounded request body exceeded.
- `429 Too Many Requests`: receiver is temporarily applying backpressure; include `Retry-After` when practical.
- `503 Service Unavailable`: persistence is not ready; plugin retains and retries the event.

Successful acknowledgement means the event is durable in WatchWeaver, not merely placed in an in-memory queue.

## Authentication and token lifecycle

WatchWeaver generates a random high-entropy Jellyfin connection token from Settings. Only a one-time plaintext value is returned. Store only an encrypted representation using the existing application secret-storage mechanism, or a one-way verifier if the product does not need to recover the token.

Capabilities:

- generate initial token;
- rotate token with an explicit grace/replace policy;
- revoke token immediately;
- show configured/not configured, creation/rotation timestamp, last successful event, and last authentication failure without revealing token material.

The receiver must use constant-time token comparison where applicable. Tokens must never appear in logs, diagnostics, API responses after creation, or frontend state snapshots.

## Idempotency and rewatch semantics

`event_id` is the idempotency key. WatchWeaver stores a source event record before acknowledging success.

Identity is scoped by Jellyfin server plus event ID so two independent servers cannot collide. A retry of the same event returns success without creating another watch. Two genuine watches of the same item must use different event IDs and become two distinct `watch_events`.

Do not deduplicate on item ID, title, timestamp, play count, or user alone.

For conflict detection, persist a compact fingerprint of immutable event identity fields. Reusing an accepted event ID for a different item/user/time returns `409` rather than silently treating it as the original event.

## Media identity mapping

For movies, prefer existing external-ID mappings in this order when available:

1. TMDb
2. IMDb
3. TVDb

For episodes, `series_id` and `season_id` identify Jellyfin's explicit hierarchy; `series_provider_ids` and `season_provider_ids` may provide portable identities. At least one stable Jellyfin or provider identity is required at each level. Map the show using provider IDs where available, then resolve/create the season and episode by the supplied identities and numbers. Never derive a series identity from the episode item ID. Episode-specific provider IDs may additionally be stored.

Jellyfin item IDs are stored as source-specific external mappings but are not globally authoritative because libraries and servers can be rebuilt.

Title/year fallback may create a candidate when provider IDs are absent, but must not merge two existing media records solely because their titles match. Ambiguous identity should be persisted as an ingestion error requiring reevaluation rather than corrupting history.

## Prompt integration

Accepted first-watch events enter the same settled-batch prompt rules used by Trakt. Jellyfin is an ingestion source, not a parallel rating/task system.

The receiver should persist accepted events first and evaluate prompts after the durable write. Prompt-evaluation failure must not cause the plugin to resend and duplicate a watch; WatchWeaver should retain enough state to retry internal evaluation independently.

Initial Jellyfin connection does not imply a historical backfill in the first slice. A separate backfill design is required before importing an existing Jellyfin library's played state because current played state does not reliably encode every historical rewatch.

## Plugin event capture

The plugin subscribes to supported Jellyfin playback and user-data events. Jellyfin can emit overlapping signals for one completed playback, so the plugin must correlate them locally.

A completion candidate should normally be established from playback-stop/finished information and confirmed by played/user-data state when needed. Routine playback-progress saves are never standalone completion events.

Correlation should consider session/play-session ID, user, item, and a bounded time window. Once one logical completion is assigned an event ID, every retry uses that same ID.

Manual watched-state changes should use `marked_played` only when the plugin can distinguish the transition from ordinary playback completion. Otherwise prefer avoiding a duplicate over inventing a second watch.

## Durable plugin queue

The plugin persists unsent events locally before attempting delivery. Queue behavior:

- bounded by configurable count/age with conservative defaults;
- FIFO delivery where practical;
- exponential backoff with jitter;
- honor `Retry-After`;
- retry network errors, 429, and 5xx;
- stop retrying structurally invalid 4xx events and expose them as rejected/dead-letter entries;
- never discard an event merely because Jellyfin restarts;
- expose queue depth, oldest queued age, last success, and last error on the plugin configuration page.

A queue overflow must be visible and noisy; it must not silently drop history.

## Plugin configuration

Jellyfin dashboard configuration should provide:

- WatchWeaver base URL;
- connection token (write-only after save);
- selected Jellyfin users;
- optional library filters if Jellyfin APIs expose stable library identifiers;
- completion behavior only where necessary; prefer Jellyfin's own played semantics rather than an unrelated WatchWeaver threshold;
- Test Connection;
- current queue/connection health;
- WatchWeaver receiver protocol version and plugin compatibility result.

Default destination policy permits private/LAN/VPN addresses. Public destinations require HTTPS and explicit acknowledgement/documentation of the authenticated reverse-proxy boundary.

## Multi-user behavior

The first release supports an explicit allowlist of Jellyfin users. Events include the upstream user ID so future per-user WatchWeaver profiles remain possible.

Until WatchWeaver has first-class profiles, all allowed users feed the instance's shared history. The setup UI must state this clearly. Do not silently merge multiple Jellyfin users without the administrator selecting them.

## Compatibility strategy

Maintain shared plugin source with explicit build targets:

- Jellyfin 10.11: .NET 9, ABI floor `10.11.0.0`.
- Jellyfin 12.0: .NET 10, ABI floor `12.0.0.0`.

Do not package Jellyfin host assemblies in plugin artifacts. CI builds and tests both targets separately.

Before declaring Jellyfin 12 support stable, revalidate against the final 12.0 packages and release notes. Preview/RC compatibility is not a promise of final compatibility.

The HTTP schema is versioned independently from Jellyfin ABI. Both plugin builds should emit schema version 1.

## Health and diagnostics

WatchWeaver Status/Settings should expose safe aggregate state:

- Jellyfin enabled/configured;
- receiver protocol version;
- last accepted event time;
- last accepted server/plugin version;
- last rejection time and stable reason code;
- authentication failure count/time;
- total accepted event count;
- whether Jellyfin is currently sufficient to satisfy the ingestion-source setup requirement.

Do not expose titles, users, item IDs, tokens, full event payloads, or watch history in downloadable diagnostics.

## Trakt independence

Once Jellyfin is configured as a valid ingestion source:

- first-run setup can complete without Trakt credentials;
- Trakt remains an optional rating/history synchronization integration for users with credentials;
- application readiness does not depend on Trakt authorization;
- Trakt outages do not make Jellyfin ingestion unavailable;
- prompt generation and local rating/review workflows continue normally.

This requires auditing any startup/configuration path that currently assumes Trakt is mandatory.

## Delivery plan

### Slice A — receiver contract and persistence

- migration for Jellyfin source-event/fingerprint/status state as needed;
- dedicated connection-token generation/revocation;
- authenticated versioned event endpoint;
- bounded JSON decoding and validation;
- durable idempotency/conflict handling;
- movie/episode media mapping;
- watch-event persistence;
- prompt-rule handoff;
- safe status fields;
- comprehensive HTTP/persistence tests.

This slice belongs in WatchWeaver and can merge before the plugin exists.

### Slice B — Jellyfin 10.11 plugin

- separate GPLv3-compatible plugin project/package;
- dashboard configuration;
- event subscription/correlation;
- durable outbound queue;
- Test Connection and health UI;
- user filtering;
- unit tests and Jellyfin 10.11 integration test.

### Slice C — Jellyfin 12.0 target

- .NET 10/12.0 build target;
- adapt registrations/interfaces only where required;
- run same behavior suite against 12.0 RC/final;
- publish ABI-specific artifact.

### Slice D — catalog and operations

- plugin repository manifest/catalog;
- stable and preview artifact metadata;
- installation/upgrade docs;
- outage/restart/duplicate/rewatch/multi-user test matrix;
- scheduled upstream compatibility check.

### Slice E — Trakt-optional onboarding

- source selection in WatchWeaver first-run setup;
- Jellyfin connection setup guidance;
- remove Trakt-wide startup assumptions;
- explain optional Trakt benefits without blocking Jellyfin-only users;
- regression tests for Jellyfin-only restart and upgrade.

## Test matrix

WatchWeaver receiver tests must cover at minimum:

- valid movie completion;
- valid episode completion with hierarchy creation;
- duplicate delivery returns success and creates one watch;
- same media watched twice with distinct IDs creates two watches;
- duplicate ID with changed immutable identity returns conflict;
- missing/invalid/revoked token;
- token rotation/revocation;
- unsupported schema/event/item type;
- malformed timestamps and episode numbering;
- request-size bound;
- provider-ID mapping and missing-ID fallback;
- ambiguous fallback does not corrupt identity;
- restart durability;
- concurrent duplicate delivery;
- prompt handoff does not make acknowledgement non-idempotent;
- safe status/diagnostic serialization;
- Jellyfin-only configuration does not require Trakt.

Plugin tests must cover at minimum:

- one completion from overlapping Jellyfin signals;
- incomplete stop creates no event;
- manual mark-played where distinguishable;
- restart with queued events;
- WatchWeaver outage/backoff/recovery;
- 429 Retry-After;
- permanent 4xx rejection visibility;
- queue bound/overflow reporting;
- two real rewatches receive distinct IDs;
- selected-user filtering;
- token never logged;
- 10.11 and 12.0 builds emit the same schema.

## Non-goals for the first implementation

- Reading Jellyfin databases directly.
- Synchronizing WatchWeaver ratings/reviews back into Jellyfin.
- Reconstructing complete historical rewatch history from Jellyfin's current played state.
- Deleting immutable WatchWeaver history when Jellyfin is marked unplayed.
- Treating Jellyfin item IDs as globally stable identifiers.
- Requiring the plugin and WatchWeaver to be upgraded in lockstep.
- Supporting speculative Jellyfin 13 APIs before they exist.
